Lattice Pane Proposal

pi-lattice · packages/pane · proposal

One pane, three depths

The recommended design, combining the rail, the inbox and the inspector from the layout study. At rest it is a quiet one-line-per-session rail. When something needs you, that goes on top. When you give it the keyboard, the chat steps aside and the selected thing is shown in full. The last screen shows the same pane when work is running in several repositories at once. Screens are drawn at 104 × 26 with the pane at its current 34 columns.

1

Quiet

Nothing is waiting. The pane is a map and stays out of the way.

  • One line per session: six sessions take six lines, where today they take twelve.
  • The repository is named once, as the header of its group. Owner appears only when it is not you.
  • Working sessions spin; idle and asleep ones are dim. Nothing is yellow, because nothing needs you.
  • The bottom line always says how to get in: alt+l.
2

Something needs you

Questions and messages appear above the tree with one line of their content.

  • You can read what is being asked without leaving the chat or opening a menu.
  • The same items are marked on their rows (?1, ✉1), so you can see where in the tree they come from.
  • The section is absent when empty, so its arrival is itself the signal.
  • The footer hint changes from “sessions” to “to answer”, with the count.
3

Focused on a session

alt+l gives the pane the keyboard. The chat is replaced by everything known about the selected session.

  • The cursor is a row highlight that keeps the row's colours; ▸ still marks the session this terminal is in.
  • The brief, roles, workspace and branch are shown: all four are already in the session's record and are displayed nowhere today.
  • Anything that session is waiting on is repeated here with its keys, so you can act without moving the cursor.
  • Every action is one key, listed along the bottom. esc puts the chat back exactly as it was.
4

Answering

Inbox items and sessions are one list. Move onto an item, or press its number, and answer it in place.

  • A yes/no question is one keypress. Today it is: open the approvals or session menu, choose “Answer it here”, then answer.
  • The full text is shown, with the asking session's brief underneath for context.
  • Opening the session is still offered, with the consequence stated: the question is dropped.
  • Messages to approve work the same way, with a and x.
5

New child

One form in place of five prompts in a row.

  • Name, kind, roles, workspace and brief are visible together, so you can go back and change one.
  • Roles are chosen from the fragments that exist, not typed from memory.
  • The tree shows where the session will appear before you commit.
  • This is the largest piece to build: the pane has to do its own text editing. The existing prompts can stay until it is ready.
6

Narrow terminal

Below the width where the side pane fits, two lines above the editor carry the same information.

  • Replaces today's compact list, which spends up to eight lines.
  • Line one is the sessions, open one highlighted, the rest counted. Line two is the first thing waiting on you.
  • alt+l opens the same focused view as screens 3 to 5, full width.
7

Several repositories

When you have work running in more than one repository, the pane groups by repository and the inbox covers all of them.

  • One inbox for everything. A question from another repository shows up here, labelled with where it is from, and is answered the same way.
  • This terminal's repository is first, marked ◆. The others follow, marked ◇, each with its own counts.
  • Quiet repositories fold to one line. A repository opens up only while something in it is working or waiting on you.
  • With one repository nothing changes: the group header is the single header in screens 1 to 5.
  • enter goes there. A session in another repository opens in this terminal like any other: Pi's tools, settings and project context move to that repository, ◆ moves to its group, and a one-line notice names where you now are. The session you left keeps working in the background.
  • - goes back to the session you were in before, so moving between two repositories is one key each way.
  • In the narrow strip, each other repository is one counter at the end of the line.

The rules behind the screens

A row, column by column

When a row runs out of room

  • The kind goes first.
  • Then the name is cut with an ellipsis.
  • The ?n and ✉n marks are never dropped.
  • A deep tree compresses its guides to one column per level, as it does today.

Status

⠹ working or starting● waiting on you● idle○ asleep or offline✓ finished✗ failed▸ open here@sam someone else's
  • Yellow means you. It is used only for things waiting on a person. A working agent is never yellow.
  • Motion means work. The spinner is the only thing that moves, and it stops when the session does.
  • Calm states are dim. Idle and asleep differ by fill, not by colour.

Build order

Each step ships on its own and leaves the pane better than before. Every step except the third works with what the host already reports. Several repositories comes third because it changes how the pane connects, and everything after it should be built on that.

Not yet checked

  • Switching to a session in another repository was tried against real Pi in RPC mode: its tools ran in the other repository afterwards. It has not been tried in the interactive interface. The shell Pi was started from stays where it was, so quitting Pi returns you there.
  • Step 3 assumes the pane can change width when it gains focus. It is laid out as a fixed 34-column item beside Pi today; I have not tried resizing it.
  • Time in state uses updatedAt, which may also change for reasons other than status. If so it needs its own timestamp.
  • The colours shown are illustrative. The real ones come from the Pi theme, which needs to offer a colour distinct from warning for “working”.
  • These are drawings, not a running build. Spinner speed and how the inbox feels when it appears mid-typing need judging live.
