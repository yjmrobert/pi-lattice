# 0017 Settings on one screen, and sessions that are told how to talk to each other

Builds on [0003](0003-roles-as-prompt-sections.md), [0009](0009-messaging-semantics.md) and [0016](0016-working-in-the-pane.md). Status: accepted and built.

A review of the project found three gaps. Sessions only knew how to talk to each other when someone remembered to give them a role: the session a person types in had none, and a child given `implementation` alone was never told to report. A parent whose child crashed, or simply answered in its own conversation and stopped, waited for ever. And settings were three keys in one file per repository, with the tree limits not settable at all.

**Decisions**

- **One table describes every setting.** `packages/protocol/src/config.ts` lists each setting's name, type, default, the environment variable that overrides it, what it does and when a change applies. The host, the settings screen, `/lattice config`, `/lattice doctor` and `docs/settings.md` all read it. A setting is added in one place.
- **Two files, and the environment over both.** A value comes from the environment, then `<repository>/.lattice/config.json`, then the person's own `<lattice home>/config.json`, then the default. The person's own file exists because someone working in several repositories should not set the same thing in each. Names nest by their dots, so the old flat keys still read.
- **The limits are settings.** The host read only its defaults before, though its own errors said to raise the limit. It now reads the settings again whenever a file changes. What a session's own messaging enforces (approval, hops, rate, size) reaches background sessions through their environment and the session open in a terminal through `lattice:settings:query`, which replaces `lattice:approval:query`.
- **The settings are a screen.** `,` in the pane, or `/lattice config`, opens every setting where the inspector is, with its value, where the value comes from and what it does. A change is written at once; `tab` switches between the two files; `x` clears a value from the file being edited. It is a pure module like the form, so it is tested without a terminal. Without room beside the pane, `/lattice config` prints the same as text.
- **Every session in a tree is told the protocol; every child is told how to report.** Two fragments, `protocol` and `reporting`, carry what used to depend on someone choosing `worker`. Which fragments are given is four settings: every session, every child, the first session of a tree, a child created with no roles. The host adds them when it creates the session, so they show in the inspector and in `list_sessions`, and `/role remove` takes one off a session.
- **The first session of a tree is not made a coordinator.** It gets `protocol` only. `coordinator` opens with "you coordinate work rather than doing all of it yourself", which is wrong for most of what people open Pi to do. `roles.root` is there for those who want it.
- **The texts pi-lattice writes are templates.** The brief wrapper, the handover note, the reminder and the notice to a parent can each be replaced by a file, in `<repository>/.lattice/templates/` or the person's own templates folder. Repository templates live in the state directory, not in `.pi/`, because the host cannot ask Pi whether a project is trusted and the state directory never comes from a clone. Values are put into a template once, so a brief containing braces is left as written.
- **One text stays fixed.** The wrapper around a message from another agent, and the line after it saying it is from a peer and not from the user, cannot be edited. It is what stops one agent giving another orders in the person's name.
- **Everything injected can be read.** `/lattice prompt` shows the role sections and the templates in effect, each with the file it comes from. `/role show <name>` prints a fragment; `/role edit <name>` and `/lattice template <name>` open one in Pi's editor and save the person's own copy; saving it empty removes the copy. The settings screen lists them as rows.
- **A child that goes quiet is reminded once, then its parent is told.** The host tracks which children owe their parent an answer: from the brief, or from more work the parent sends, until the child sends its parent anything. A background child that ends its turn while owing one, with no question open, no mail waiting and no children of its own still working, is told so by pi-lattice. If it ends another turn the same way, its parent receives a message with intent `stopped`. A child whose process dies before it reported produces the same message. `reports.remind` switches the reminder off.
- **A result marks a session done.** A child that sends its parent a message with intent `result` shows `✓` until its parent sends it more work. While the pane is at rest, a done session whose descendants are all done or asleep folds to one line with a count.

**Consequences**

- Children now carry three fragments by default (`protocol`, `reporting`, `worker`), about 650 words of system prompt. Emptying `roles.tree` and `roles.children` removes them.
- What owes whom is kept in the host's memory. After a host restart nobody is reminded for work given before it; a crash is still reported for any child that never finished.
- The reminder is a turn the child would not otherwise have had. A model that answers in text and never calls `send_message` costs one extra turn per piece of work.
- `lattice:approval:query` is gone; an older messaging extension paired with a newer pane falls back to its environment and the default.
- Project role fragments (`.pi/lattice/roles/`) reach a child in its own worktree only when they are committed, since a worktree holds what git tracks.
